# Automatic project understanding

The framework supplies engineering behavior; each repository supplies its facts. A user can start substantive work in an unfamiliar repository without preparing AGENTS.md or an onboarding brief. Discovery is part of the authorized task, not a startup daemon or a separate prerequisite.

## First substantive task

Read the closest instructions and existing authoritative sources. Establish only the map needed for the task: repository/package boundaries, manifest and lockfile pins, actual run/check commands from scripts and CI, affected architecture, and the release/mutation boundary. Missing files are gaps to investigate, not permission to invent commands, accounts, environments or completion claims. Scale discovery to the task; a small bug does not initiate a whole-project audit.

Use code, schema, tests and current provider evidence to resolve facts independently. Ask only for an unavailable decision or authority that materially blocks the next action. A new greenfield project acquires this map as authorized design and implementation decisions are made.

## Later tasks and changes

There is one evolving baseline, not an unconditional full scan per request and not an immutable cached snapshot. Use existing project docs and available native task context; inspect the current checkout, changed contracts and affected dependencies. If previous context is unavailable, recover the minimum from authoritative sources rather than trusting absent recall. Refresh only the relevant map after a stack, architecture, command, schema or delivery change. A status question is a readback, not a rediscovery trigger.

Latest user steering overrides an older goal objective, plan, summary or compacted context. After steering, compaction or resume, reconcile the remaining lanes before consequential work. Never reuse a prior confirmation, MFA value, clipboard value or target selection as current authority.

Before consequential provider operations, always revalidate the exact account/project/environment, credential class, selectors and authority. Previous knowledge cannot establish present external state. A passing check is reusable only while its source digest, command/configuration, target and relevant inputs remain unchanged.

Represent credential knowledge as safe locator metadata only: service, environment, authoritative secret location, account/project, credential class, owner/recovery path and last verified date. An inventory or memory entry proves where to look, not that a credential is valid now. Do not read, print, move or persist the secret merely to prove existence; access it only when the authorized operation needs it and prevent disclosure through output, docs, memory and retained artifacts.

## Improving knowledge

During work, distinguish hypotheses from observations. After meaningful verification, update the existing authoritative contract, nearby documentation or regression test when a durable discovery would prevent future mistakes and the update is in scope. Prefer references to manifests, commands and existing docs over copied values. Do not turn every file read into a note or create a mandatory project description.

Ephemeral progress, selected batches, blockers and check results belong to native tasks. Optional native memory follows the user's settings and write authority; do not create memory engines, hidden caches, generated startup payloads, transcript injection or automatic memory writes. Cross-session understanding does not depend on enabling memory.

## Engineering acceptance

The parent owns the user's outcome, acceptance criteria, dependency decisions, integration and final evidence. Model independent work as lanes; assign independent substantive leaf implementation to native workers with a concrete evidence return and separate worktrees. A blocker stops only dependent lanes, and the goal is blocked only when every remaining lane is blocked. Select checks from affected behavior and the actual execution path, including build/deployment scripts. Local green tests do not establish hosted migration, deployment, Browser or human acceptance.

For shared mutable environments, finish or explicitly resolve the active acceptance cycle before another batch invalidates it. Independent previews may proceed in parallel. Report source identity, environment and implementation/merge/CI/migration/deployment/user-acceptance states separately. Never assign a universal numeric quality score in place of these criteria.

Before expanding work discovered during execution, classify it: an acceptance-critical bounded repair stays in the lane; an independent defect becomes another lane; a cross-application refactor, new infrastructure, public surface or other material expansion requires explicit user or project-contract authority.

External workflow state changes use read/compare/preview/mutate/read-back against one exact object and the latest relevant evidence. A stale state, mismatched owner/status/version, ambiguous identifier or partial batch stops that lane. Consequential actions additionally require a current-turn, single-use confirmation bound to the action, target, account, environment, amount/count and price or irreversible effect; compaction/resume or any material change invalidates it.

## Verification scope

`framework-project-behavior-eval.py` uses isolated local repositories and native Codex execution. Its independent graders test unambiguous successful commands, product behavior and the fixture input schema. Free-form documentation semantics remain unverified; keywords cannot establish correct knowledge. These are controlled fixtures, not evidence of live Property acceptance. Policy classification, deterministic diagnostics, behavioral fixtures, and actual project acceptance remain separate evidence levels.
