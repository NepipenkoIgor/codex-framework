# Runtime efficiency and automatic challenge

Native Codex owns goals, tasks, worktrees, agent lifecycle, approvals, compaction and monitoring. The global agreement is the automatic default across Git projects; no project onboarding file or user request for debate is needed.

## Ordered delivery gates

Every native task has a bounded human-style evidence exchange. Trivial and read-only work gets one compact challenger exchange before its conclusion. Material code work follows one state machine: capability and identity preflight; acceptance criteria plus a pre-mutation tester/architect challenge and parent adjudication; implementation; runtime and visible-UI debug; a post-implementation tester challenge; any applicable independent high-risk review; then PR. Evidence from a later state never backfills a skipped earlier state. Green unit, headless, or CI results do not replace visible in-app Browser evidence for a runnable web path, and a provider website never replaces an available authenticated CLI/API/connector.

The pipeline is surface-aware, not silently weaker. The desktop app can provide visible in-app Browser acceptance. Codex CLI and IDE do not expose that Browser; when UI acceptance is required there, the result remains unverified and PR delivery waits for a desktop/browser handoff. Missing provider authentication likewise pauses the dependent lane before planning or coding while independent safe work may continue. The framework cannot pre-authorize accounts or copy credentials across machines.

## Work and waiting

Complete coherent batches against explicit acceptance criteria and source/config/environment identity. Represent independent work as lanes with explicit dependencies and acceptance. A blocker stops only its dependent lane; the whole goal becomes blocked only when every remaining lane is blocked. Assign independent substantive leaf implementation to native workers in separate worktrees only when lanes are independent and expected critical-path benefit exceeds child startup/context cost; coupled work may remain parent-owned. Shared mutable environments stay serialized. A checkpoint neither spends an execution allowance nor cancels authority to continue fixing a CI defect. Reuse unchanged evidence. A current progress question gets an immediate checkpoint from verified state, not a heartbeat. Read a live operation once, retain its handle and cursor, and use native attached waits rather than model-driven micro-polls. A timeout is not a failed process; continue observing the same handle. Native heartbeats serve explicitly requested recurring or later monitoring and stay quiet without actionable changes. “Finish”, “babysit”, “do not stop”, and other terminal persistence wording continue the current goal; they do not authorize a heartbeat or schedule. Never add a local scheduler or lifecycle hook.

Before a delivery batch, declare its ticket scope, owner, acceptance and an expected response/tool/time/uncached-input budget using the closest measured baseline. If usage exceeds that budget or evidence changes the task class, replan the remaining batch before more repetitive work. A budget never ends authorized work or weakens verification. Keep one active delivery batch per writer; independent native workers may own separate worktrees and batches. Count provider waiting separately from active work and use attached waits rather than sleep polling.

Latest user steering supersedes stale goals, plans, summaries and compacted context. Before consequential work after steering, compaction or resume, reconcile the remaining lanes and revalidate current authority. Never replay an old confirmation, MFA value, clipboard value or target selection.

## Evidence-based challenge

The unit of debate is one bounded decision or delivery batch, not every command, wait, leaf-agent step or check. The batch has one identified challenger and a stable batch ID. Each finding has a globally unique batch-scoped ID, severity, concrete claim, affected acceptance rows, and blocked stages. The developer explicitly accepts and repairs or rebuts each finding with a typed evidence pointer. Verification runs before the same challenger marks that finding `resolved`, `withdrawn`, or `unresolved`; only then does the parent adjudicate before mutation or result acceptance. A closure summary is valid only when it enumerates exactly the observed finding IDs and states. A false-positive test is not a product defect, agreement and prose-only claims are not proof, and agent voting is prohibited. A challenger may return `no findings` only with the bounded scope and executed checks. Reuse the challenger for targeted repair verification; leaf agents do not recursively spawn critics and no exchange repeats without new evidence.

Material implementation, fixes, architecture decisions and delivery receive both pre-mutation and post-implementation challenges. Trivial or read-only tasks receive one compact challenger exchange rather than a self-check. Only material security, schema/API, migration, deployment, concurrency, permissions or cross-system risk receives exactly one later fresh read-only reviewer against an immutable neutral evidence bundle. Ordinary material work does not pay for that independent review. The independent pass supplements rather than replaces the developer/challenger exchange.

Debate conformance is versioned and per-finding. A complete native task family is `compliant` only when each finding preserves challenge → developer response → verification → same-challenger disposition → parent adjudication with verified evidence. Related findings may share one bounded native follow-up, but each keeps its own nonce, verification, disposition and adjudication; a challenger does not become a standing review service across unrelated batches. Native root call and child receipt must contain identical encrypted-message ciphertext. Native `FileChange` events bind implementation paths. Before the plan challenge, bounded read-only repository, CLI identity, target and capability preflight plus exact task-worktree creation are allowed; implementation or external mutation is not. Contradictory identity, order or outcome is a `violation`; missing child traces, unsupported native event types or incomplete family capture are `unverifiable`, never inferred success. Historical audit and release certification are separate scopes. A later exchange cannot retroactively repair a skipped pre-mutation gate, and a changed contract revision, source SHA, configuration digest, environment or target invalidates only the affected evidence.

The high-risk reviewer receives an immutable diff and neutral request/criteria/contracts/checks. No-history spawn does not remove every source of runtime context: injected task memory invalidates strict independence. Report an unavailable boundary honestly and do not restart the same review under a new name. One review/revision bounds that review; it never blocks subsequent authorized CI repair. Materially new risk may require its own review.

Delivery stages are declared by the discovered task contract rather than forced into one universal list. A local library may require implementation and local/pre-merge checks but no deployment; a hosted application may additionally require PR-only checks, merge identity, post-merge hosted checks, environment mutation, runtime acceptance, or external stakeholder state. A required red or pending pre-merge stage blocks merge. A required pending post-merge stage does not erase completed implementation or a valid merge, but it blocks delivery acceptance. A non-applicable stage needs a typed reason, and a later stage never backfills skipped earlier evidence.

## Authority, state and scope

Credential continuity is locator metadata, never secret storage: service, environment, authoritative secret location, account/project, credential class, owner or recovery path and last verified date. Do not read or print a secret merely to confirm that it exists. Access a value only for the authorized operation, through a path that keeps it out of prompts, tool output, documentation, memory and retained artifacts.

Derive an authorization inventory from the current user request: already-authorized delivery actions, read-only checks, new consequential actions that need exact confirmation, and prohibited operations. An explicitly requested PR, merge, named-branch synchronization or board transition remains authorized for that unchanged target and scope during ordinary goal continuation; do not ask for the same authorization again. A new purchase, deletion, publication, production mutation or material target/scope/price change requires a current-turn, single-use confirmation of exact action, target, account, environment, amount/count and effect. It expires after use, compaction/resume, reauthentication or any consequential change; a broad earlier approval cannot cover a new effect.

Before a WIP count, board mutation, or worktree cleanup, reconcile ticket ID, native task/thread, writer, worktree, branch, stage and latest provider readback. GitHub assignee is a board field, not proof that this agent owns another agent's work. Preserve dirty or differently owned worktrees, including work started by another tool or model. Goal status claims require the successful native goal result for the current task; prose and inferred progress do not establish `paused`, `blocked` or `complete`.

External workflow mutations use one transaction shape: read the exact object and latest evidence; compare current and expected state; preview the exact change; mutate only that object; read it back. Stale state, an unexpected owner/status/version, an ambiguous identifier or a partial batch stops that lane. Mutation-request success is not read-back proof.

Classify newly discovered work before acting. A bounded repair required by current acceptance remains in the lane; an independent defect becomes a separate lane; cross-application refactors, new infrastructure, new public surfaces and other material expansion require explicit user or project-contract authority.

## Worktree lifecycle

Before repository mutation, use a task-owned native worktree even for a single writer. Verify current path/branch and other active writers. Git supplies tracked instructions/config; inspect ignored files and copy only named necessary local configuration with permissions preserved and verified environment identity. Never bulk-copy credentials, Git internals, build caches or another writer's dirty files. Regenerate dependencies and provider links for the target. If a user explicitly requires their dirty work, isolate and transfer only that agreed diff after inspecting it.

After all required checks for the final identity pass, use the authorized native PR/merge flow. Successful deploy is separate from CI and user acceptance. Synchronize only the named clean base branch; verify merge ancestry and equality to the remote. Remove only clean task-owned worktrees and merged task branches. Do not force-delete dirty/unmerged work, another model's checkout, or a durable installed framework source. Exact task ownership follows observed native task/git state; no local queue or ownership daemon is added.

## Evidence levels

Policy lint proves declared clauses and known textual contradictions, not native context isolation. Policy classification checks hypothetical decisions. Tool-enabled fixtures check actual traces plus independent filesystem/runtime outcomes. Product acceptance still requires the real target. Token structure success and behavioral warnings are separate: cached input is a subset of input, reasoning a subset of output, and parent/child counters cannot be summed without provenance. Report measured values rather than promises of savings.

Delivery fixtures use an explicit native permission profile extending `:read-only`, with only their disposable fixture area writable and command network access disabled. Collector artifacts live outside that area. This is evaluator isolation, not a production permission override. A macOS native sandbox probe verified that the permitted write succeeds and the collector-side write is denied; portability of this enforcement remains subject to each native runtime.
